# Архитектура TrafficSignalStudio — план развития

## Цель

Развивать собственную настольную программу для Windows без обязательной зависимости от SUMO. Геометрия, полосы, маршруты и сигнальные объекты должны храниться как отдельные сущности, а не выводиться из рисунка интерфейса.

## Принципы

1. **Сначала модель данных, затем визуализация.** GUI отображает дорожную модель, но не является её единственным хранилищем.
2. **Явные связи полос.** Разрешённые манёвры и траектории задаются соединениями «полоса → полоса». Нельзя угадывать поворот по направлению подхода или автоматически считать любой поворот допустимым.
3. **Сохранение совместимости.** Новые поля должны иметь версии схемы и миграции; существующие проекты нельзя молча перезаписывать.
4. **Воспроизводимые расчёты.** В сценариях фиксируются входные данные, параметры модели и seed генератора случайных чисел.
5. **Проверяемые нормативные выводы.** Каждая проверка должна указывать документ, пункт, редакцию/дату действия, область применимости и результат. Неизвестные или не проверенные требования отмечаются как требующие экспертной проверки.
6. **Разделение расчётных уровней.** Оценочная модель очередей не называется микросимуляцией. Микросимуляция должна моделировать отдельные транспортные средства, скорость, ускорение, дистанцию, перестроения, блокировки и взаимодействия с сигналами и пешеходами.

## Текущий первый этап: граф полос

Модуль app.simulation.lane_routes задаёт полосы, разрешённые манёвры, направленные соединения и явную геометрию соединения. Поиск маршрута пока использует BFS по числу соединений, а не по времени или расстоянию. Геометрия хранится в координатах модели; преобразование координат экрана и генерация плавных кривых будут отдельным этапом.

## Ограничения

Граф полос сам по себе не гарантирует соответствие ПДД или ГОСТ. Для этого нужны данные о знаках, разметке, сигнальных группах, геометрии, условиях видимости и проверенные правила. Импорт линий OSM/GeoJSON не считается автоматически корректной полосной моделью.
