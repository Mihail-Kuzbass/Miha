# Спринт №1 — Android foundation и первый рабочий проект

> Документ фиксирует контракт первого спринта и сверяет его с текущим состоянием Android-ветки. Он не означает, что все пункты уже прошли проверку на физическом устройстве.

## 1. Цель и результат

Создать независимое Android-приложение TrafficSignalStudio Mobile на Kotlin и Jetpack Compose, которое работает на Android 10+, не требует сети для базового сценария и позволяет:

1. открыть приложение и выбрать одиночный перекрёсток или сеть;
2. создать проект из шаблона;
3. открыть геометрический редактор;
4. сохранить проект в локальное хранилище;
5. закрыть и повторно открыть приложение, затем восстановить проект;
6. собрать воспроизводимый debug APK через CI.

Спринт формирует устойчивый фундамент для собственного расчётного и имитационного ядра. SUMO, 2ГИС и облачный сервис не являются обязательными зависимостями.

## 2. Границы спринта

### Обязательно для foundation

- Android-приложение в каталоге mobile/, отдельно от Windows/Python-прототипа.
- Gradle multi-module и единый Version Catalog.
- Kotlin, Jetpack Compose, Material 3.
- minSdk 29, Java 17.
- Доменная модель без зависимости от Android и Compose.
- Геометрические шаблоны перекрёстков.
- Локальное TSS/JSON-хранилище в приватном каталоге приложения.
- Главное меню, выбор режима и список локальных проектов.
- Первый экран редактора со схемой сверху.
- Unit-тесты доменной модели и геометрических алгоритмов.
- CI, который проверяет тесты, собирает APK и сохраняет артефакт.

### Не является критерием завершения именно foundation

Полная калиброванная микросимуляция, официальный нормативный расчёт, сертифицированное заключение о соответствии ПДД/ГОСТ, полноценный импорт 2ГИС/OSM, синхронизация с облаком и release-подпись. Эти возможности развиваются отдельными спринтами. Если их прототипы уже присутствуют в текущей ветке, это не заменяет самостоятельные критерии точности и приёмки.

### Текущие модули

| Gradle path | Назначение | Разрешённая ответственность |
|---|---|---|
| :app | Android entry point, сборка приложения, навигация верхнего уровня, главное меню | Android lifecycle, запуск экранов, связывание зависимостей |
| :core:model | Kotlin/JVM доменные типы | Модели и инварианты; без Android SDK, Compose, файловой системы |
| :core:geometry | Геометрия, шаблоны, анализаторы и существующие прототипы расчётов | Чистые алгоритмы; не обращаться к UI и Android Context |
| :data:local | Хранение TSS/JSON в filesDir | Преобразование доменной модели в формат хранения и обратно |
| :feature:editor | Compose-экран редактора | Представление и пользовательские команды; не владеть форматом JSON |

### Целевая декомпозиция ядра

Следующие модули пока являются архитектурным планом, а не утверждением об их наличии в Gradle:

- :core:conflicts — геометрические конфликты манёвров;
- :core:signals — группы сигналов, фазы и временные состояния;
- :core:safety — защитные интервалы, освобождение конфликтных зон, проверка совместимости;
- :engine:simulation — индивидуальные агенты ТС и пешеходов;
- :engine:coordination — коридоры, циклы, сдвиги и сетевые планы;
- :engine:optimization — оптимизация по ограничениям и целевым функциям;
- :engine:analytics — показатели и отчёты;
- :data:import — OSM/GeoJSON и другие адаптеры;
- :feature:home, :feature:signals, :feature:simulation, :feature:coordination, :feature:analytics — отдельные пользовательские функции.

Извлекать их следует после фиксации публичных интерфейсов и тестовых наборов. Не создавать пустые модули только ради красивого дерева каталогов. Сейчас часть анализаторов и расчётных прототипов находится в :core:geometry; это временная концентрация, которую нужно разнести без изменения результатов тестов.

### Направление зависимостей

```text
:app ───────────────► :feature:editor
  │                         │
  ├──► :data:local ─────────┤
  ├──► :core:geometry ◄─────┤
  └──► :core:model ◄────────┘

:data:local ───────────────► :core:model
:core:geometry ────────────► :core:model
:core:model ───────────────► Kotlin/JVM only
```

Запрещённые зависимости: core:model -> Android/Compose, core:geometry -> app, data:local -> feature:*. UI передаёт команды и получает результат; движок не должен импортировать Compose-классы.

## 6. Модели данных Kotlin

Текущая доменная модель размещена в:

- mobile/core/model/src/main/kotlin/ru/trafficsignalstudio/model/ProjectModels.kt;
- mobile/core/model/src/main/kotlin/ru/trafficsignalstudio/model/VehicleModels.kt.

Основные агрегаты:

1. ProjectDocument — корневой документ, ID, имя, временные метки, schemaVersion.
2. RoadNetwork — список перекрёстков, межузловые транспортные связи и настройки координации.
3. Intersection — тип, центр, подходы, дорожные сегменты, узлы соединения, островки, связи полос и план сигнализации.
4. Approach / Lane — подход и его полосы; у полосы есть разрешённые манёвры и направление относительно узла.
5. RoadSegment / RoadSegmentLane — свободно нарисованная ось дороги, ширина, полосы, уровень высоты и тип сегмента.
6. LaneConnection — явная связь «въездная полоса → выездная полоса». Это идентификатор движения в текущей модели, а не подпись вида «движение 1».
7. SignalPlan / SignalPhase — набор фаз и ID разрешённых связей полос.
8. NetworkTrafficLink — связь между конкретным движением одного перекрёстка и движением следующего.
9. NetworkCoordinationSettings — общий цикл, скорость прогрессии, опорный узел, направление и сдвиги.
10. VehicleModel / VehiclePose — габаритная и динамическая модель класса ТС и состояние отдельного экземпляра.

### Правила представления величин

- Геометрические координаты и размеры хранятся в метрах (Double).
- Скорость в модели ТС хранится в км/ч; ускорение и замедление — в м/с².
- Время сигналов — целые секунды.
- Approach.headingDegrees и VehiclePose.headingDegrees — градусы по часовой стрелке от севера карты.
- LaneFlowDirection описывает направление относительно узла: въезд или выезд.
- LaneConnection ссылается на ID подходов и полос, а не на их отображаемые названия.
- ID сущностей — строки UUID; отображаемые подписи формируются отдельно от ID.
- ProjectDocument.CURRENT_SCHEMA_VERSION сейчас равен 8.

### Что ещё не является полноценной частью сохраняемой модели

Нужны отдельные доменные типы для спроса по времени и классам ТС, пешеходных потоков, сценария запуска, seed и параметров случайности, состояния каждого агента на шаге симуляции, результатов/агрегатов, маршрутов и нормативных ссылок с редакцией документа. Также нужно отдельно формализовать SignalHead и SignalGroup. Эти сущности нельзя подменять временными полями Compose или вычислять заново из подписей UI.

Подробная карта текущих и будущих типов вынесена в DOMAIN_MODEL.md.

## 7. Главное меню и поток создания проекта

### Текущая реализация

MainActivity.kt содержит TrafficSignalStudioApp, MainMenuScreen и HomeScreen.

Текущий пользовательский поток:

1. MainMenuScreen: «Одиночный перекрёсток», «Сеть перекрёстков», «Выход».
2. HomeScreen: выбор шаблона, последние проекты, возврат в меню.
3. Диалог шаблонов: 3-, 4-, 5-, 6-сторонние узлы, Y/T-образный, круговое движение и геометрические заготовки развязок.
4. Создание ProjectDocument, сохранение через ProjectJsonStore.
5. Открытие IntersectionEditorScreen.

### Требования к завершённому меню

- На первом экране видны название продукта, назначение и два главных сценария.
- После выбора сценария доступны «Создать» и список последних проектов.
- У проекта показываются имя, число перекрёстков и дата изменения.
- Пустое, загрузочное и ошибочное состояния не должны выглядеть одинаково.
- Ошибка чтения/записи показывается человеку; повреждённый файл не удаляется автоматически.
- Возврат назад не должен молча терять несохранённые изменения.
- На узком экране список прокручивается, основные действия остаются доступными.
- Базовая навигация работает в авиарежиме.

## 8. Первый экран редактора

### Минимальная компоновка

1. Верхняя панель: назад, имя проекта, имя активного узла, сохранить.
2. Рабочее поле сверху: схема в плане, масштаб, панорамирование, линейная шкала.
3. Панель инструментов: выбор/редактирование, линия, ломаная, дуга, мост, съезд, островок.
4. Панель параметров: выбранный подход, число/ширина полос, направление движения, разрешённые манёвры.
5. Панель связей: человекочитаемая пара «откуда → куда» с привязкой к ID.
6. Панель диагностики: ошибки геометрии и предупреждения отдельно; расчётные конфликты не называть нормативным нарушением без правила и источника.

### Текущее состояние

IntersectionEditorScreen.kt уже реализует рабочее поле Canvas, жесты масштабирования/панорамирования, режимы рисования и редактирования, сегменты, островки, выбор модели ТС, связи полос, анализ конфликтов и доступ к предварительным экранам моделирования. Экран сейчас длинный и прокручиваемый; на следующих итерациях его следует разделить на рабочую область и контекстную панель, не уменьшая полезную высоту Canvas.

### Требования к поведению редактора

- Геометрия хранится в метрах, Canvas только отображает её с преобразованием координат.
- Панорамирование и масштаб не меняют геометрию проекта.
- Отмена точки относится к текущей незавершённой операции.
- Редактирование узла изменяет только выбранный объект; ID остальных объектов сохраняются.
- Уровень высоты моста/эстакады учитывается отдельно от планового пересечения.
- Автоматическая привязка узлов не должна создавать соединение только потому, что две линии визуально пересеклись.
- Связь полос задаётся явным выбором въездной и выездной полосы.
- В UI показываются названия подходов, полос и манёвров; технические ID остаются внутренними.
- Ошибки валидации геометрии и результаты анализа конфликтов имеют разные категории.
- Длительные расчёты не выполняются на главном потоке UI.

## 9. Локальное хранение и версия документа

Текущий адаптер: data/local/ProjectJsonStore.kt. Файлы хранятся в приватной директории приложения filesDir/projects/ как <projectId>.tss.json; сеть и разрешение на доступ к общему хранилищу для этого не нужны.

Обязательные свойства:

- стабильный ID проекта;
- версия схемы;
- явная сериализация полей;
- совместимость при добавлении необязательных полей;
- отказ с понятным сообщением при неизвестной будущей версии;
- безопасная запись через временный файл и атомарную замену;
- резервная копия перед миграцией/опасной заменой;
- сохранение повреждённого исходника для восстановления;
- тесты round-trip: модель → JSON → модель.

Текущее хранилище уже выполняет JSON round-trip вручную, но запись пока использует прямой writeText, а ошибки чтения в loadAll() пропускаются через mapNotNull. Это нужно усилить: сначала добавить атомарную запись и диагностируемый результат загрузки, затем подключать миграции. Не повышать schemaVersion без миграционного теста.
