# Доменная модель TrafficSignalStudio Mobile

## 1. Назначение

Этот документ описывает текущие Kotlin-модели и отделяет их от сущностей, которые ещё предстоит добавить для полноценной микросимуляции и инженерной координации. Источник истины для реализованных типов — исходный код core:model, а не этот текст.

## 2. Где находятся модели

- ProjectModels.kt — проект, дорожная сеть, перекрёстки, подходы, полосы, дорожные сегменты, связи полос, фазы и координация.
- VehicleModels.kt — классы транспортных средств, номинальные параметры и положение экземпляра.
- ProjectJsonStore.kt — текущий JSON-адаптер, не доменная модель.

Модуль :core:model — Kotlin/JVM. В нём нельзя использовать android.content.Context, Compose, Android View, файловые операции или зависимости от UI.

## 3. Текущая модель проекта

Упрощённая схема агрегатов:

```text
ProjectDocument
└── RoadNetwork
    ├── Intersection[]
    │   ├── Approach[]
    │   │   └── Lane[]
    │   ├── RoadSegment[]
    │   │   └── RoadSegmentLane[]
    │   ├── RoadJunctionNode[]
    │   ├── SafetyIsland[]
    │   ├── LaneConnection[]
    │   └── SignalPlan
    │       └── SignalPhase[]
    ├── NetworkTrafficLink[]
    └── NetworkCoordinationSettings
```

### Корневой документ

```kotlin
data class ProjectDocument(
    val schemaVersion: Int = CURRENT_SCHEMA_VERSION,
    val id: String = UUID.randomUUID().toString(),
    val name: String,
    val createdAtEpochMs: Long = System.currentTimeMillis(),
    val updatedAtEpochMs: Long = System.currentTimeMillis(),
    val network: RoadNetwork = RoadNetwork()
) {
    companion object {
        const val CURRENT_SCHEMA_VERSION = 8
    }
}
```

Один документ может содержать один или несколько перекрёстков. Для одиночного проекта RoadNetwork.intersections содержит один элемент. Для сетевого проекта — несколько элементов и связи между их движениями.

### Геометрия

- Point2D(xMeters, yMeters) — локальные координаты в метрах.
- Approach(id, name, headingDegrees, lanes) — подход к узлу.
- Lane(id, index, widthMeters, allowedMovements, flowDirection) — полоса на подходе.
- RoadSegment — независимая осевая линия с шириной, числом/описанием полос, высотным уровнем и видом сегмента.
- RoadJunctionNode — общий топологический узел, связывающий концы дорожных сегментов.
- SafetyIsland — контур островка безопасности и его высотный уровень.

RoadSegmentKind различает прямой сегмент, ломаную, дугу, мост и съезд. LaneTravelDirection задаёт направление по или против осевой линии. LaneFlowDirection задаёт въездное/выездное направление полосы относительно перекрёстка. Эти два enum решают разные задачи и не должны объединяться.

### Движения и сигнализация

```kotlin
data class LaneConnection(
    val id: String = UUID.randomUUID().toString(),
    val fromApproachId: String,
    val fromLaneId: String,
    val toApproachId: String,
    val toLaneId: String
)

data class SignalPhase(
    val id: String = UUID.randomUUID().toString(),
    val name: String,
    val greenConnectionIds: Set<String>,
    val greenSeconds: Int = 30,
    val flashingGreenSeconds: Int = 3,
    val yellowSeconds: Int = 3,
    val allRedSeconds: Int = 1
)
```

В текущей версии LaneConnection является явной связью «въездная полоса → выездная полоса». MovementKind хранит тип разрешённого манёвра полосы. Отображаемая подпись движения должна строиться из названий подходов, индексов полос и вида манёвра. Не показывать пользователю внутренние UUID или условные номера без контекста.

SignalPhase.greenConnectionIds ссылается на ID связей полос. Это базовая модель назначения зелёного; полноценные группы сигналов, отдельные светофорные секции, стрелки и состояния пешеходных светофоров требуют расширения модели.

### Сеть и координация

NetworkTrafficLink хранит:
- ID исходного и целевого перекрёстка;
- ID движения на исходном узле и ID движения на целевом узле;
- долю потока;
- длину связи в метрах;
- признак активности.

NetworkCoordinationSettings хранит общий цикл, скорость прогрессии, опорный перекрёсток, направление координации и сдвиги фаз/циклов. Валидатор должен дополнительно проверять, что все указанные ID существуют в текущем RoadNetwork; проверок диапазонов чисел в конструкторе недостаточно для целостности всей сети.

## 4. Модель транспортного средства

VehicleClass содержит легковые, малотоннажные, грузовые, сочленённые грузовые, автобусы, троллейбусы, мотоциклы и велосипеды.

VehicleModel хранит:
- габариты: длину, ширину, высоту;
- колёсную базу, передний и задний свес;
- минимальный радиус поворота;
- максимальную скорость;
- ускорение и служебное замедление;
- точку сочленения для сочленённого транспорта;
- минимальный зазор и желаемый временной интервал следования.

Это номинальные инженерные значения, а не заводские сертифицированные характеристики конкретной модели автобуса или автомобиля. Для расчётов пользователь должен иметь возможность заменить их параметрами конкретного ТС.

VehiclePose хранит ID экземпляра, ссылку на модель, координату, направление, скорость и ускорение. Это геометрическое состояние для отображения; для детерминированной симуляции потребуется отдельное состояние агента с маршрутом, текущим манёвром, полосой, временем входа, длиной очереди и служебными флагами.

## 5. Инварианты и единицы

1. Геометрия и расстояния — метры.
2. Скорость в VehicleModel/VehiclePose — км/ч; перед применением динамических формул переводить в м/с на границе алгоритма.
3. Ускорение/замедление — м/с².
4. Времена фаз — секунды.
5. Направление — градусы по часовой стрелке от севера.
6. Все ссылки между сущностями — стабильные ID, а не позиции элементов списка.
7. Ширина полос, размеры ТС, скорость и временные интервалы должны быть конечными числами и проверяться на допустимый диапазон.
8. Координаты не должны зависеть от плотности пикселей, масштаба Canvas или ориентации экрана.
9. Уровень высоты дороги отделяет путепровод от конфликта в одном уровне; визуальное пересечение на плане не доказывает реальный конфликт.
10. Подписи UI не входят в расчётные ключи и не являются первичными идентификаторами.

## 6. Версионирование и хранение

- Текущая версия ProjectDocument.CURRENT_SCHEMA_VERSION: 8.
- Формат: JSON, расширение .tss.json.
- Хранилище: приватный filesDir/projects/.
- Текущий код сериализует поля вручную через org.json.

До расширения схемы необходимо:
- определить миграции N -> N+1;
- иметь тестовые JSON-образцы для каждой поддерживаемой версии;
- проверять неизвестную будущую версию до чтения данных;
- сохранять резервную копию перед миграцией;
- писать сначала во временный файл, затем атомарно заменять основной;
- возвращать диагностируемую ошибку повреждённого проекта, а не молча исключать файл из списка.

Не повышать версию схемы только из-за добавления необязательного вычисляемого поля. Изменение семантики или обязательной структуры требует миграции.

## 7. Целевые модели для следующего этапа

Следующие структуры являются проектным направлением, а не уже реализованными классами. Их следует добавлять после согласования формата TSS и тестов.

```kotlin
data class TrafficDemandProfile(
    val id: String,
    val connectionId: String,
    val totalVehiclesPerHour: Double,
    val classFlowsPerHour: Map<VehicleClass, Double>,
    val startSecond: Double,
    val endSecond: Double
)

data class PedestrianDemandProfile(
    val id: String,
    val crossingId: String,
    val pedestriansPerHour: Double,
    val startSecond: Double,
    val endSecond: Double
)

data class SimulationScenario(
    val id: String,
    val name: String,
    val durationSeconds: Int,
    val timeStepSeconds: Double,
    val randomSeed: Long,
    val trafficDemand: List<TrafficDemandProfile>,
    val pedestrianDemand: List<PedestrianDemandProfile>
)

data class SimulationResultSummary(
    val scenarioId: String,
    val engineVersion: String,
    val completedAtEpochMs: Long,
    val enteredVehicles: Long,
    val dischargedVehicles: Long,
    val meanDelaySeconds: Double,
    val maximumQueueMeters: Double
)
```

Для классов ТС сумма потоков по классам не должна превышать общую интенсивность. Остаток должен обрабатываться явным правилом, а не теряться. Интервалы спроса не должны перекрываться неоднозначно для одной и той же сущности. Seed и версия движка обязательны для воспроизводимости результатов.

Дополнительно понадобятся:
- SignalHead, SignalGroup, SignalAspect и типы пешеходных секций;
- MovementTrajectory с геометрией и идентификаторами конфликтных зон;
- runtime-состояние отдельного автомобиля/пешехода;
- маршрут и выбор полос;
- политика инцидентов/ДТП с явным включением и воспроизводимым случайным seed;
- нормативная ссылка: документ, редакция, дата действия, пункт, область применения, источник и уровень обязательности;
- результат расчёта с исходными параметрами, предупреждениями и трассировкой применённых методик.

## 8. Минимальный набор тестов модели

- сериализация и обратная загрузка полного проекта;
- round-trip для каждого типа дорожного сегмента;
- сохранение ID подходов, полос, движений и межузловых связей;
- сохранение направлений въездных/выездных полос;
- отклонение недопустимых числовых параметров;
- проверка ссылочной целостности NetworkTrafficLink;
- отклонение неизвестной будущей версии документа;
- миграция предыдущей версии с проверкой неизменности геометрии;
- детерминированность сценария при одинаковом seed;
- независимость моделей от Android/Compose.

## 9. Инженерная оговорка

Наличие модели и алгоритма в приложении не означает автоматически нормативную корректность. Для каждого расчёта нужны документированная методика, редакция исходного норматива, область применимости, граничные условия, тестовые примеры и независимая проверка. Интерфейс должен различать геометрическую ошибку, расчётное предупреждение и подтверждённое нарушение конкретного правила.
